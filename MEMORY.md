## Verified facts (from official docs, 2026-09-16)

- **SDK**: `@nimiq/mini-app-sdk` (npm), v0.1.0, MIT licensed. Usage: `import { init } from '@nimiq/mini-app-sdk'; const nimiq = await init()`. `init()` waits for the Nimiq provider and gives typed access. Source: https://nimiq.dev/mini-apps/
- **Nimiq Provider API** (source: https://nimiq.dev/mini-apps/api-reference/nimiq-provider):
  - `listAccounts()` → `string[]` of user-friendly addresses. Requires user confirmation. Throws `PermissionDeniedError`.
  - `sign(message)` where `message: string | { message: string, isHex?: boolean }` → `{ publicKey: string, signature: string }` (hex). Requires user confirmation. Throws `PermissionDeniedError`.
  - `isConsensusEstablished()` → `boolean`. No confirmation needed.
  - `getBlockNumber()` → `number`. No confirmation needed.
  - `sendBasicTransaction({ recipient, value, fee?, validityStartHeight? })` → `string` tx hash. Requires confirmation. `value` is in Luna (integer).
  - `sendBasicTransactionWithData({ recipient, value, data, fee?, validityStartHeight? })` → `string` tx hash. Requires confirmation. Example in docs uses a plain string for `data` (e.g. `'mic check'`) — **not** shown hex-encoded, so plain short ASCII reference strings appear supported. Exact byte-size limit is NOT documented — treat as UNKNOWN until tested against a real send (Spike S3).
  - Staking methods exist (`sendNewStakerTransaction`, etc.) — irrelevant to NimCare, not used.
  - **`getTransactionByHash` / `getTransactionsByAddress` are NOT part of the Mini App Provider API** — they are Nimiq JSON-RPC node methods (see below), a different surface.
- **Local dev testing** (source: https://nimiq.dev/mini-apps/development/load-local-mini-app):
  - Requires Node.js 22+.
  - `npm run dev -- --host`, then open the LAN URL from Nimiq Pay's Mini Apps → Custom URL field. Phone and dev machine must share Wi-Fi.
  - Dev server over plain HTTP is **not a secure context** — `crypto.randomUUID()` and similar secure-context-only APIs may be unavailable in the phone WebView. Use `crypto.getRandomValues()` or a UUID library with a fallback.
  - **Testnet exists and is usable for demo funding**: long-press the settings button for 10 seconds in Nimiq Pay to reveal a hidden dev menu, switch to Testnet, then use "Get free NIM" to claim 110,000 Luna (1.1 NIM) per request. This resolves the "no funded wallet" operational risk for Spikes S2/S3 and for the live demo — a human with the Nimiq Pay app can self-fund a test wallet without needing us to source real NIM.
  - Testnet switch only affects Nimiq operations; EVM/dual-chain features stay on mainnet unless configured otherwise (not relevant to NimCare, no EVM usage planned).
- **Recommended stack** (source: https://nimiq.dev/mini-apps/tutorials/mini-app-tutorial): official tutorial offers Vite + (Vue|React|Svelte) + TypeScript. No pinned versions documented — use current npm-published stable majors at scaffold time and commit the lockfile.
- **JSON-RPC methods exist** for `getTransactionByHash` and `getTransactionsByAddress` (source: https://nimiq.dev/rpc/methods/get-transactions-by-address, https://nimiq.dev/rpc/methods/get-transaction-by-hash) — these run against a Nimiq **node's own RPC server**, not a documented public hosted endpoint. `getTransactionsByAddress` supports a `max` param (default 500) and `startAt` (exclusive, before-hash pagination), returns newest-first, includes reward transactions.
- **No confirmed public/hosted Nimiq RPC endpoint** was found in current docs during this research pass. `nimiq.watch` is a community block explorer (https://nimiq.watch/) but its API contract for PoS is not confirmed. Running your own RPC node (`--rpc` flag) is the documented path. **This is a real, unresolved dependency for server-side transaction verification (Spike S4)** — see PROJECT_PLAN.md Assumption Register.

  - Public GitHub repo, MIT License, no hardcoded secrets, must be fully functional (no prototypes).
  - Max 250-word written description; optional demo video.
  - Gambling/chance-based mechanics explicitly prohibited — reinforces the master prompt's non-goals.
  - The rules page's own dates read "August 24 – September 18, **2024**" — this is almost certainly a stale copy-paste year on the organizer's page; the user-supplied deadline of **2026-09-18 23:59 UTC** is treated as authoritative per instruction precedence, but this discrepancy should be re-checked against the live page before final submission.

## Spike results from reading the actual installed SDK (`node_modules/@nimiq/mini-app-sdk@0.1.0/dist/*.d.ts` and `.js`, ground truth, 2026-09-16)

This resolves several PROJECT_PLAN unknowns with certainty (from source, not docs prose):

- **`sendBasicTransactionWithData`** (Spike S3, partially resolved): confirmed signature `{ recipient: string, value: number, fee?: number, data: string, validityStartHeight?: number }` → `Promise<string | ErrorResponse>`. `data` is a plain string (not required hex). Byte-limit still unconfirmed (not in types) — keep references short.
- **`sign(message)`**: confirmed `message: string | { message: string, isHex?: boolean }` → `Promise<{ publicKey: string, signature: string } | ErrorResponse>`. Failures are returned as a resolved `ErrorResponse` object (`{ error: { type, message } }`), **not necessarily a thrown/rejected promise** — client code must check for an `error` key on every wallet-method result, not just wrap in try/catch.
- **Transaction verification (Spike S4, schema now resolved)**: the SDK ships a `TransactionInfo` type — the real shape of a transaction lookup response: `{ hash, blockNumber, timestamp, confirmations, size, relatedAddresses, from, fromType, to, toType, value, fee, senderData, recipientData, flags, validityStartHeight, proof, networkId }`. `from`/`to` are addresses, `value`/`fee` are Luna integers, `senderData`/`recipientData` presumably carry the `data` field we set (need to confirm which one holds our `NC:D:<id>` reference — likely `recipientData` since Nimiq's PoW/PoS basic-with-data transactions attach data to the recipient side, but this needs confirmation against one real transaction before relying on it).
- **RPC wire format (Known, from source)**: `RPCServer.call()` POSTs `{ id, jsonrpc: '2.0', method, params }` as JSON to the configured RPC URL and expects a response shaped `{ result: { data: <payload> }, error?: { message, data } }` — it specifically reads `response.result.data`, not `response.result` directly. Our backend's own RPC client must replicate this exact envelope (Albatross-style JSON-RPC with a `data`/`metadata` wrapper), not assume a flat `result`.
- **No default/baked-in RPC URL**: `NimiqProvider` only pre-wires the wallet methods (`listAccounts`, `sign`, `sendBasicTransaction*`) through the Nimiq Pay host adapter without needing an RPC URL. Any other JSON-RPC method (including `getTransactionByHash`) throws `"No RPC URL configured"` unless `rpcUrl`/`rpc` was passed to `init()`/the provider constructor or `setRPCUrl()` was called. **This confirms there is no hidden public default endpoint we can rely on** — `NIMIQ_RPC_URL` must be explicitly provisioned (self-run node or a documented/provided endpoint), which remains the one real, unresolved operational gap for server-side verification.
- Practical consequence for `TRD.md`: our backend can either (a) run its own tiny JSON-RPC client hitting the same wire format directly (recommended — no need to import the browser-oriented SDK server-side), or (b) reuse the SDK's exported `RPCServer` class server-side since it's plain `fetch`-based and has no browser-only dependencies besides `events` (which Node provides natively). Decision: (a), a minimal dependency-free client in `server/services/nimiqRpc.ts`, to avoid pulling a browser-targeted package into the API.

## 2026-09-18 hardening pass — real evidence (supersedes earlier "no confirmed RPC endpoint" claim)

- **Public RPC confirmed live and reachable**: `https://rpc.nimiqwatch.com`, documented at https://nimiq.dev/rpc/integrations/raw, actually called from this environment during hardening. `getBlockNumber` returned a real current mainnet block number; `getTransactionByHash` and `getTransactionsByAddress` (params: `[address, max, startAt]` — the third param is required, `null` if unused) returned real transaction data. **The earlier claim that "no confirmed public/hosted Nimiq RPC endpoint was found" is stale and superseded** — a real, working public endpoint exists and this build now defaults `NIMIQ_RPC_URL` to it.
- **Wire format confirmed exactly as implemented**: `{jsonrpc, method, params, id}` request, `{result: {data, metadata}}` / `{error: {code, message, data}}` response. A not-found transaction returns a JSON-RPC `error`, which our client already treats as "not yet visible" rather than a hard failure.
- **`TransactionInfo` schema confirmed field-for-field** against a real live mainnet transaction response: `hash, blockNumber, timestamp, confirmations, size, relatedAddresses, from, fromType, to, toType, value, fee, senderData, recipientData, flags, validityStartHeight, proof, networkId` all present and correctly typed. `recipientData`/`senderData` are hex-encoded, as expected.
- **New field discovered**: `executionResult: boolean` appears on real responses (confirmed `true` on a real validator transaction) but is **not** part of `@nimiq/mini-app-sdk`'s bundled `TransactionInfo` TypeScript type. Added as optional to our own `TransactionInfo` and checked (`executionResult === false` → mismatch) in `verifyTransaction.ts`. Its presence on plain basic-transfer (non-staking) transactions is unconfirmed — treated as optional, not required.
- **Mainnet `networkId` observed live: `24`.** `NIMIQ_NETWORK_ID` remains opt-in/unset by default (we haven't independently confirmed the testnet networkId or which network the demo will actually run against), but `24` is documented in `.env.example` as the observed mainnet value for whoever configures production.
- **Real crypto signature verification implemented and proven**: `@nimiq/core` (`PublicKey.fromHex`, `Signature.fromHex`, `PublicKey.verify`, `PublicKey.toAddress().toUserFriendlyAddress()`) works synchronously in Node (no async WASM init needed server-side, confirmed by reading `nodejs/index.mjs`). The Nimiq Signed Message digest format — `SHA256(0x16 + "Nimiq Signed Message:\n" + decimalByteLength + message)` — was independently corroborated against Nimiq's own Hub/Keyguard docs (23-byte prefix, decimal-ASCII length, then message) and proven with a live round-trip using a freshly generated real keypair (valid signature accepted; tampered message, wrong public key, and address/key mismatch all correctly rejected). See `server/src/services/nimiqSignedMessage.ts` and its test file.
- **Critical bug found and fixed via this real-crypto testing**: `nimiqAddress.ts`'s validation regex required 9 four-character groups *after* the `NQ\d{2}` prefix (i.e. 10 groups / 40 chars total). Real Nimiq addresses are 9 groups / 36 chars **total**, with `NQ\d{2}` forming the first group. The bug would have rejected every genuine wallet address in production; it went undetected in the original build because that session's smoke test used a hand-typed, incorrectly-long fake address that happened to satisfy the buggy regex. Fixed to 8 repetitions after the prefix; re-verified against real `@nimiq/core`-generated addresses and a real address seen in a live RPC response.
- **Transaction-to-CareDrop binding**: confirmed hex-decoding `recipientData` and comparing to the stored `NC:D:<id>` reference correctly rejects a real, live, on-chain mainnet transaction (fetched from `rpc.nimiqwatch.com`) that doesn't belong to a given CareDrop — proving the verifier makes a real network call and a real decision, not a stub.
- **Scoring page re-read and independently re-verified** (https://miniappscompetition.com/scoring, is a client-rendered Nuxt app — a raw `curl` only returns an unrendered shell, so this was checked with both `WebFetch` and a real browser render, 2026-09-18): the live page currently shows **45 / 25 / 15 / 10 / 5 = 100 points total** — Functionality/Reliability/Usefulness 45, Nimiq Pay & Nimiq Integration 25, Real Usage 15, Design & UX 10, Builder Promotion Checklist 5 — which **matches the original planning session's numbers exactly**, not the "25/25/25/25/5 = 105" breakdown described in the 2026-09-18 hardening instructions. This is flagged as a direct discrepancy rather than silently resolved either way: the live page is the highest-priority source per Hackathon OS rules ("current official documentation wins"), so canonical docs are being *kept* at 45/25/15/10/5/100 rather than changed to the newer-but-unverifiable numbers. If the competition genuinely changed its scoring and this page is stale/cached for some viewers, that needs a human to confirm directly with the organizer before submission — do not trust either source blindly at that point.

## 2026-09-18 pivot — overlap audit + Cashlink spike (surprise-first media CareDrop)

**Checkpoint**: tagged `pre-media-caredrop-pivot` at commit `312b0c4` before this pivot began (pushed to origin). Rollback: `git checkout pre-media-caredrop-pivot`.

**Overlap audit (quick, web search only — not exhaustive)**:
- **Nimiquette**: "records why a NIM payment was sent and lets the recipient acknowledge it" — closest conceptual neighbor (payment + reason + acknowledgement), but no media, no surprise-first reveal, no persistent Loop/Memory history. NimCare differentiates via media-rich CareDrops and an automatically-forming relationship history.
- **Ralli**: social/challenge-participation category (public), not private 1:1 gifting — clearly different axis.
- **KashLink**: per the pivot brief, a link-based NIM sender — Cashlinks-as-infrastructure would overlap here if NimCare merely wrapped a raw Cashlink link. Mitigated by keeping any funding rail (direct NIM, in practice) as internal plumbing behind a NimCare-branded share URL/reveal experience, never exposing a raw payment link as the product surface.
- No substantive copying risk identified for the chosen direction (private, media-first, reciprocal Loop history) against what search turned up for these named products.

**Cashlink spike result: FAIL / NOT VIABLE in the current Mini App architecture — concluded from strong, converging evidence rather than a live device test:**
1. `@nimiq/mini-app-sdk`'s `NimiqProvider` (read directly from its shipped source during the previous hardening pass, re-confirmed here) exposes exactly: `listAccounts`, `sign`, `isConsensusEstablished`, `getBlockNumber`, `sendBasicTransaction`, `sendBasicTransactionWithData`, and the staking `send*StakerTransaction`/`sendStakeTransaction`/etc. methods. **There is no `createCashlink`/`manageCashlink` on this provider at all.**
2. Cashlinks live exclusively in `@nimiq/hub-api` (`CREATE_CASHLINK`/`MANAGE_CASHLINK` request types), a *separate* integration surface built for external websites talking to the Nimiq Wallet **Hub** — a popup/redirect flow to `hub.nimiq.com`, fundamentally different from the Mini App model where Nimiq Pay itself injects `window.nimiq` directly into the WebView specifically so apps *don't* need popups/redirects to an external wallet page.
3. Nimiq's own developer-center issue tracker documents a known Nimiq Pay iOS bug where a Mini App WebView opening another layer on top of the wallet can get stuck stacked, requiring a force-quit to recover — independent evidence that stacking a Hub popup flow on top of a Mini App WebView is not a supported, safe interaction pattern today.
4. Conclusion: attempting to wire `@nimiq/hub-api` into a Mini App running inside Nimiq Pay would mean asking the WebView to open (or navigate to) an entirely separate Nimiq-hosted page for wallet interaction, discarding the Mini App SDK's already-authenticated `window.nimiq` session for no compatible reason, with a documented history of WebView-stacking bugs on at least one platform. This is exactly the "major WebView friction" the pivot brief said to stop at without a live device to verify against.

5. Further confirmed via the Hub "Advanced" guide (https://nimiq.dev/hub/guide/advanced, user-supplied link, fetched 2026-09-18): Hub API requests are explicitly redirect-based (`new HubApi.RedirectRequestBehavior(returnUrl, state)`), i.e. a full top-level page navigation away to `hub.nimiq.com` and back — not a popup or iframe call that could stay layered inside a Mini App WebView. Navigating a Mini App's WebView away from its own origin to complete a Hub redirect, then somehow returning into the same live Mini App session inside Nimiq Pay, is not a documented or supported round trip anywhere in the fetched docs.

**Decision (per the pivot brief's own Go/No-Go gate)**: retain `sendBasicTransactionWithData()` (already built, hardened, and proven live in production) as the **only** funding rail. `funding_type` is still modeled as an enum (`DIRECT_NIM` now; `CASHLINK` reserved but unimplemented) so this isn't a dead end if a future Mini App SDK version adds Cashlink support — but nothing is built against it today, and nothing claims it works.

**Practical consequence for the "surprise-first, no pre-known recipient" goal**: since funding requires a recipient address at broadcast time (no Cashlink to defer that), the sender picks the recipient from an existing Loop *or* the CareDrop is created with `recipient_wallet = NULL` and the sender still triggers the real transaction once a wallet is bound — see the new binding flow below. This preserves "recipient never accepts a relationship first" even without Cashlinks: the *Loop* is still implicit/automatic, it's only the *payment recipient address* that must be known at send time, which is unavoidable for any direct on-chain NIM transfer regardless of funding rail.

## 2026-09-18 real-device blank-screen hotfix

**Reported symptom**: on a real physical Nimiq Pay device, after a successful wallet connect + sign-in, NimCare rendered a completely blank warm-white screen with no visible error.

**Root cause: CONFIRMED**, via three independent pieces of evidence, not assumed:
1. **Code inspection**: `HomeScreen` computed `other = l.member_a_wallet === address ? l.member_b_wallet : l.member_a_wallet` for every row `GET /api/pairs/mine` returned, then called `shortenAddress(other)`. The old (pre-pivot) `shortenAddress(address: string)` called `address.replace(...)` with no null guard. `GET /api/pairs/mine` had no filter at all — it returned every `pair` row for the wallet, including legacy pre-pivot PENDING invite rows where `member_b_wallet` is still `NULL`.
2. **Live production data**: queried the real production Postgres directly (read-only, count-only — no addresses printed). Of 39 total `pair` rows, **1** had `member_b_wallet IS NULL` and `status = 'PENDING'` — a genuine leftover from the old invite/accept flow, sitting in the exact table the current Home screen queries.
3. **Reproduced the crash directly**: `shortenAddress(null)` → `TypeError: Cannot read properties of null (reading 'replace')`, confirmed by direct execution, not inferred. Because no React Error Boundary existed anywhere in the app, this render-time exception took the entire tree down to a blank screen with nothing in the DOM and no visible error — exactly the reported symptom.

**Fixes applied** (all layers, not just the one that happens to be tripped today):
- `server/src/routes/pairs.ts` `GET /pairs/mine`: now filters `WHERE status = 'ACCEPTED' AND member_b_wallet IS NOT NULL` — legacy rows are excluded from the current Loop UI, not deleted (no destructive migration; they remain in the DB for historical/audit purposes and are harmless as long as nothing renders them as a current Loop).
- `app/src/lib/luna.ts` `shortenAddress`: now accepts `string | null | undefined`, returns `'Unknown wallet'` for anything else, never throws. Explicitly scoped as UI crash protection only, not an authorization mechanism.
- `app/src/screens/Home.tsx`: added `resolveOtherWallet()` as a second, independent validation layer (checks both members are non-empty strings and that the current wallet is actually one of them) — a malformed row is silently skipped (with a dev-only console warning), never rendered. Also gave `api.careDropTypes()` a `.catch()` it was previously missing (an unhandled promise rejection on a secondary endpoint could otherwise leave the CareDrop type picker permanently empty with no feedback) and a visible retry state.
- `app/src/components/ErrorBoundary.tsx`: new root Error Boundary wrapping the whole app in `App.tsx`. Any future uncaught render exception now shows a branded "Something went wrong — your wallet and funds are safe" recovery screen with Try again / Back to NimCare, instead of a blank page. Never surfaces a raw stack trace to the user; logs to console in dev only.
- `app/src/diagnostics.ts`: temporary, explicitly non-sensitive stage-marker logging (`SESSION:listAccounts:ok`, `SESSION:nonce:ok`, `SESSION:sign:ok`, `SESSION:verify:ok`, `HOME:loops:loaded`, `HOME:types:loaded`, `HOME:render:ok`) added to `session.tsx` and `Home.tsx`, console-only, to help pinpoint exactly where a future on-device failure occurs if one happens again. Intended to be removed once device verification confirms this fix and no further diagnosis is needed.

**Tests added**: `server/src/integration.test.ts` — a new test inserts a legacy-shaped `PENDING`/`member_b_wallet IS NULL` row directly (the current API can no longer create one) and proves `/pairs/mine` excludes it. 24/24 tests passing (up from 23).

**What this fix does NOT claim**: the coding environment has no physical Nimiq Pay device. This is `HOTFIX CODE: PASS` at the code/data level (root cause confirmed, all layers hardened, regression test passing, quality gates clean, deployed to production) but `DEVICE FIX: UNVERIFIED` until a human re-runs the exact on-device repro steps and confirms Home now renders instead of blanking.

## 2026-09-18 real-device transaction internal_error investigation

**Reported symptom**: on the real device, past the blank-screen hotfix, the flow reaches the actual payment step — recipient selected, content created, 0.5 NIM amount chosen, review confirmed — and Nimiq Pay shows "Waiting for your approval in Nimiq Pay…" then fails with `internal_error` and no transaction hash. The failure is inside `provider.sendBasicTransactionWithData()`, before `api.submitPayment()` — so backend RPC/verification is not a plausible cause of this specific failure (confirmed by code read: `Composer.tsx`'s `create()` only calls `api.submitPayment()` after `sendCareDropPayment()` returns `ok: true`).

**A real, confirmed bug found and fixed while investigating** (not the same as confirming the root cause of `internal_error` itself — that still requires the device retest below): `app/src/nimiq/provider.ts`'s `sendCareDropPayment` collapsed *every* `ErrorResponse` from the SDK into `kind: 'PermissionDenied'`, always showing the user "Transaction cancelled" — regardless of the SDK's own `error.type` field (`ErrorResponse` is `{ error: { type: string; message: string } }` per `@nimiq/mini-app-sdk`'s `provider.d.ts`). This means a prior `internal_error` (or any other real cause) was never distinguishable from the user simply canceling — the UI, and any future log, would have said the same thing either way. Fixed with a real classifier (`classifyProviderFailure`) that inspects `error.type`/thrown `Error.name`/`.message`/a nested `.cause.message`, maps known types to the messages specified in this hotfix's brief, and preserves `internal_error` as its own `kind: 'InternalError'` rather than mislabeling it. Verified directly (Node reproduction script, no frontend test runner exists in this repo) against 10 representative failure shapes — see this session's transcript; `internal_error` now classifies distinctly, `PermissionDeniedError`/`InvalidTransactionError` (as either an `ErrorResponse.type` or a thrown `Error.name`) map correctly, unrecognized types surface their real message instead of a generic one.

**Recipient address validation was regex-only** (`server/src/nimiqAddress.ts`): checked group/character-count format but not the two ISO 7064 MOD 97-10 check digits Nimiq addresses embed. Replaced with `@nimiq/core`'s own `Address.fromUserFriendlyAddress()` parser — the authoritative check Nimiq Pay itself uses. Verified directly: a genuine address (from `KeyPair.generate()`) passes; a format-correct address with one character of its checksum group flipped is rejected with "Invalid checksum"; malformed strings are rejected with "Wrong length"/"Wrong country code". New test file `server/src/nimiqAddress.test.ts` plus an added case in `integration.test.ts` covering this via the real `POST /api/caredrops` endpoint. This closes a real gap: a regex-valid-but-checksum-invalid address could previously reach the point of attempting a real transaction, for Nimiq Pay to reject internally — a plausible (not confirmed) contributor to an `internal_error`-shaped failure if the real device's copied/typed recipient address happened to have this property.

## 2026-09-18 differential fix: normal CareDrop internal_error vs. working diagnostics

**Decisive real-device evidence**: Test A (`sendBasicTransaction`) and Test B (`sendBasicTransactionWithData` + arbitrary data) both **PASS with real tx hashes** — same wallet, same recipient, same network, consensus true, 1 Luna. The normal CareDrop flow (through `Composer.tsx`) still returns `internal_error` even at 1 Luna. This rules out network/consensus/balance/provider-in-general and isolates the bug to a difference between the diagnostic payload and the normal-flow payload.

**Root cause, confirmed by code inspection**: `Composer.tsx`'s `create()` called `sendCareDropPayment({ recipient, ... })` using the local `recipient` variable (`recipientWallet || customAddress.trim()`) — the *raw client input*, un-canonicalized — instead of `drop.recipient`, the value `POST /api/caredrops` actually validated and echoed back. Compounding this: `normalizeAddress()` (server) was whitespace-collapse only, not real canonicalization — any correctly-ordered, checksum-valid character sequence parses successfully via `@nimiq/core` regardless of where its spaces are (verified directly: a compact no-space input and an irregularly-5-char-grouped input both parse to the identical canonical form), but the old normalization preserved whatever grouping the caller happened to submit rather than re-deriving the canonical one. A manually-typed/pasted diagnostic-screen address (typed once, cleanly) is far less likely to hit this than a real Loop-selected or previously-stored address subject to whatever spacing survived a copy/paste chain.

**Fix**: `Composer.tsx` now always uses the server-returned `createdDrop.recipient` for payment, never the raw local `recipient`. `server/src/nimiqAddress.ts`'s `normalizeAddress()` now returns `Address.fromUserFriendlyAddress(...).toUserFriendlyAddress()` — real canonical output — instead of whitespace-collapsing. Verified: compact, padded-whitespace, and irregularly-5-char-grouped representations of the same address all normalize to the identical canonical string; a checksum-invalid address throws rather than silently normalizing.

**Also fixed while here** (per this hotfix's explicit brief):
- **Stale retry state**: "Try again" previously called `setStep('review')`, which on the next "Create surprise" tap called `create()` again — creating a **second, orphaned `AWAITING_PAYMENT` CareDrop row** with a fresh id/reference every retry. Now `retry()` reuses the *same* already-created `drop` (calling `attemptPayment(drop)` directly) unless creation itself never succeeded, in which case it falls back to a fresh `create()`. Still always an explicit human tap, never automatic — satisfies "no auto-retry" and "don't mix references between records" together.
- **Payload diagnostics**: `sendCareDropPayment` now logs the actual recipient value (public, not sensitive) alongside amount/reference/byte-length, and flags NBSP/zero-width/newline/BOM characters in either the recipient or reference via `hasInvisibleOrNonstandardChars()` (codepoint-set check, not a regex — an earlier regex-literal attempt at this same check broke the build because the file-write tooling rendered the ` `-style escapes as literal invisible characters in the source, which is itself a small, ironic confirmation of exactly the class of bug being guarded against here).
- **Temporary debug UI**: on payment failure, `Composer.tsx`'s error screen now shows a collapsible `<details>` block with the exact canonical recipient, value, reference, reference byte length, and classified error type/message — for the human to screenshot during the next retest. Must be removed once confirmed fixed, along with `TxDiagnosticScreen`'s Test C (added: `sendBasicTransactionWithData` using the *exact* `NC:D:<10 chars>` normal-CareDrop reference format, not the arbitrary `NC:DIAG:TEST` string, to distinguish "any data breaks it" from "this specific reference format breaks it").

**What this fix does NOT claim**: no real device access from this environment. The raw-recipient bug is a confirmed, real defect independent of whether it is *the* cause of `internal_error` — it's a legitimate bug either way (using un-canonicalized client input for an on-chain destination is wrong regardless), but only the next device retest (ideally including Test C) can confirm whether it was the sole cause, a contributing cause, or whether another difference remains.

## 2026-09-18 timing/lifecycle investigation (Test A/B/C all PASS, normal flow still fails)

**Ground truth accepted from real-device evidence**: Test A (`sendBasicTransaction`), Test B (`sendBasicTransactionWithData` + arbitrary data), and Test C (`sendBasicTransactionWithData` + the exact normal `NC:D:<10 chars>` reference format) all **PASS with real tx hashes** — same wallet, recipient, network, value, consensus true. This was run *after* the differential hotfix (canonical `drop.recipient` fix), so the normal flow's payload should now be byte-identical to Test C's — yet the normal flow still returns `internal_error`. This rules out payload content as the remaining variable and narrows the search to *process/timing* differences between the two code paths.

**What static code inspection can and cannot prove here**: traced `sendBasicTransactionWithData` through `@nimiq/mini-app-sdk`'s installed source (`dist/provider.js`, `dist/index.js`). The npm package's `init()` only polls `window.nimiq` every 50ms until the native app injects it (near-instant once Nimiq Pay's WebView has loaded — not a bottleneck by the time a user reaches Composer's review step, minutes into the session). Critically, `window.nimiq`'s actual method implementations (`listAccounts`, `sign`, `sendBasicTransactionWithData`, etc.) are **not implemented in this npm package** — the package ships only the polling helper and TypeScript types; the real implementation is entirely native (Swift/Kotlin) code injected into the WebView, invisible to any static inspection of the JS dependency tree. This means the internal behavior of the native bridge — whether it requires a request to occur within a live "user gesture" window, whether it queues/serializes requests, exact timeout behavior — cannot be proven or disproven from source alone. This is stated plainly rather than guessed at.

**Concrete, code-inspection-verified differential** between the working diagnostic path and the normal Composer path (exhaustive grep across `app/src` for every call site of `getProvider`/`connectWallet`/`signMessage`/`sendCareDropPayment`/provider methods — confirmed no other component calls the provider during the payment window, ruling out concurrent-provider-request as a *currently present* risk):

| Aspect | Working (Test A/B/C) | Normal CareDrop flow |
|---|---|---|
| Async calls between tap and `sendBasicTransactionWithData` | 2 (`isConsensusEstablished`, `getBlockNumber`) | 4-6+: optional photo upload (multipart, network-bound, can be seconds on a real photo over mobile data), `POST /api/caredrops` (network round trip), plus the same 2 preflight calls |
| React state updates before the provider call | 0 (diagnostic screen has no intermediate state transitions) | At least 2 (`setStep('sending')`, `setDrop(createdDrop)`) before `attemptPayment` even starts its own async work |
| Component identity | Same component (`TxDiagnosticScreen`) throughout | Same component (`ComposerScreen`) throughout — confirmed no unmount/remount between tap and send; `step` changes are internal state, not route changes |
| Time elapsed since the originating tap, at the moment `sendBasicTransactionWithData` is actually called | Sub-second (two fast provider RPCs only) | Unbounded — dominated by photo upload duration plus one backend round trip; on real mobile data this is very plausibly multiple seconds |
| Concurrent provider calls in flight | None (verified: no other code path invokes the provider while Composer is on-screen) | None found by the same audit — ruled out as a *currently present* risk, not fabricated evidence of the contrary |

**Leading, unproven hypothesis**: elapsed time / intervening async work between the user's tap and the wallet call is what distinguishes the two paths. This is architecturally analogous to browser "transient user activation" requirements (the same category of restriction behind popup blockers and the Payment Request API) — a well-established pattern for exactly this class of native-bridge API, though NOT confirmed for Nimiq Pay specifically from any documentation or source available here. **Per this investigation's explicit instruction, production was not refactored around this hypothesis without device-side proof.** Instead, three proof mechanisms were built:

1. **Test D — "Replay exact payload"**: `Composer.tsx`'s error screen now has a dedicated "Replay exact payload (diagnostic)" button. It performs *only* the provider send against the already-created real CareDrop (no re-upload, no re-create, no reference/amount change) — functionally the same operation `retry()`/"Try again" already does since the earlier differential hotfix, but distinctly labeled so a device tester can report exactly which action they took. If this succeeds where the original single-tap attempt failed, that's strong evidence for the timing hypothesis, since it's the *same* payload sent from a fresh, minimal-latency tap.
2. **Test E (E1-E5)** and **Test F (F1-F3)** added to `TxDiagnosticScreen`: E varies the amount of delay/harmless-fetch work inserted before a known-working (Test C) send; F varies whether the consensus/block-height preflight calls happen before the send. Each is an explicit, separate human tap — nothing runs automatically.
3. **Prepared-Card Test** (`PreparedCardTest.tsx`, `?diag=prepared`): splits "create a real CareDrop" and "send it" into two genuinely separate user gestures, using real backend data rather than a synthetic diagnostic payload — the closest thing to proving/disproving the hypothesis against production data without touching production code.

**A real, independently-confirmed bug fixed while investigating** (regardless of whether it is *the* cause): the "Create surprise" button in the review step had no `disabled` guard and no synchronous re-entrancy check. A rapid double-tap could fire `create()` twice before React's asynchronous re-render (triggered by `setStep('sending')`) removed the button, each invocation independently calling `createCareDrop` and attempting a provider send — creating a duplicate CareDrop row and, if both taps got far enough, a duplicate transaction request. Fixed with a synchronous `useRef` in-flight guard (checked and set before any `await`, unlike a React state update which only takes effect on the next render) in `create()`, `retry()`, and `replayExactPayload()`. Also added per-attempt correlation IDs (`PAYMENT_ATTEMPT:<id>:start/provider-call/success/error`) and elapsed-time-since-tap on every `PAYMENT:*` stage marker, so a future device log can directly show whether two attempts ever overlap.

**Production error UX**: the generic `InternalError` message is now the exact text requested — "We couldn't open the Nimiq Pay transaction. Please try again." — never the raw string `internal_error`.

**What this investigation does NOT claim**: `ROOT CAUSE` is **not proven**. No physical device access exists in this environment; Test D/E/F/Prepared-Card are built and ready but not run. The double-tap guard is a real, independently-justified fix, not a guess at the `internal_error` cause. The timing/lifecycle hypothesis remains the strongest untested lead, not a confirmed finding — see `TASKS.md` Phase 14 for the exact next device steps.

## 2026-09-18 backend root cause: recipient foreign-key violation (CONFIRMED)

**Root cause: CONFIRMED**, not inferred — via a real production Vercel log for `POST /api/caredrops`:

```
error: insert or update on table "pair" violates foreign key constraint "pair_member_b_wallet_fkey"
  at async findOrCreateLoop (/vercel/path0/src/routes/pairs.ts:119:3)
  at async <anonymous> (/vercel/path0/src/routes/caredrops.ts:67:18)
code: '23503'
table: 'pair'
constraint: 'pair_member_b_wallet_fkey'
detail: 'Key (member_b_wallet)=(<address>) is not present in table "wallet".'
```

The surprise-first product lets a sender name any valid Nimiq address as a recipient, including one that has never opened NimCare — but `pair.member_b_wallet` and `caredrop.recipient_wallet` both carry a foreign-key reference to `wallet(address)`, and until this fix, only `POST /api/auth/nonce` ever inserted a `wallet` row. `findOrCreateLoop`'s `INSERT INTO pair (..., member_b_wallet, ...)` therefore failed for any never-before-seen recipient — this is the actual, decisive explanation for `internal_error`: `Prepare (backend only)` in the Prepared-Card test failed *before* any Nimiq Pay call because the backend itself was failing on `POST /api/caredrops`.

**Why every prior diagnostic transaction test (A/B/C) passed and the Prepared-Card "Prepare" step is what finally caught it**: A/B/C sent NIM directly via the wallet provider, with no backend involvement at all — there is no `caredrop`/`pair` row for a raw provider call. The normal Composer flow and the Prepared-Card test's "Prepare" step both go through `POST /api/caredrops`, which is exactly where the FK violation lives. The timing/lifecycle investigation (previous entry) was a reasonable, honestly-labeled *unproven hypothesis* given the evidence available at the time; this new evidence (Prepare failing before any wallet call) is what actually locates the bug. **The timing hypothesis is REJECTED as the root cause** — not because it was disproven experimentally, but because the newly available evidence points to an earlier, backend-only failure that fully explains the symptom without needing a timing effect at all.

**A real, structural blind spot in every prior test**: every existing integration test that involves a recipient (including the ones added in earlier hotfixes this same day) called `loginWallet(b)` for the recipient *before* creating a CareDrop — which, as a side effect, always inserted the recipient's `wallet` row first via `/api/auth/nonce`. This meant the entire test suite, despite reaching 33 passing tests, never once exercised the actual first-time-recipient path that real users hit constantly (sending a surprise to someone who has never used the app — the product's core use case). New tests were added that deliberately never authenticate the recipient first.

**Fix**: new `server/src/services/wallet.ts` exports `ensureWalletRecord(address)` — an idempotent `INSERT ... ON CONFLICT(address) DO NOTHING`, explicitly documented as *not* an authentication mechanism (no `public_key`, grants no session, no trust). Called in `POST /api/caredrops` for both the recipient and (defensively) the sender, before `findOrCreateLoop`. `auth.ts`'s `/nonce` handler now calls the same shared helper instead of its own duplicate inline insert. When that recipient later actually authenticates, the existing placeholder row is updated in place (verified by test: `public_key` goes from `NULL` to the real value, no duplicate row — `address` is the primary key, so duplication is structurally impossible regardless).

**Auth security preserved**: a placeholder wallet row grants nothing. `requireSession` is unchanged — still purely session-token based, itself only issued after real Ed25519 signature verification (`verifyNimiqSignedMessage`). Verified by a new test: an unauthenticated request to a placeholder recipient's CareDrop gets 401; a different wallet's valid session gets 403; only after the real recipient actually signs in do they get access.

**Error logging improved**: the global Express error handler now logs structured, safe fields for Postgres errors (`code`, `constraint`, `table`, `route`, `method`) instead of the raw error object (which for this exact bug included the recipient's address in its `detail` field). The client-facing response is unchanged — still the generic `{ error: 'internal_error' }` in all cases.

## Decisions and why

- **Persistence**: use SQLite for local/dev persistence (via `better-sqlite3`) with a schema designed to be portable to Postgres later, rather than fabricating a managed Postgres instance we don't have credentials for. Documented as a Phase 7 human action to swap in real Postgres for production.
- **Transaction verification approach**: implement verification against a configurable Nimiq RPC endpoint (`NIMIQ_RPC_URL` env var) using the documented `getTransactionByHash`/`getTransactionsByAddress` methods. If no RPC endpoint is available in a given environment, the CareDrop is kept in `PAYMENT_SUBMITTED` (never force-advanced to verified) and the UI shows an explicit "verification pending — RPC not configured" state rather than fabricating a VERIFIED result.
- **On-chain reference encoding**: use a short plain-text reference in `sendBasicTransactionWithData`'s `data` field (e.g. `NC:D:<short-id>`), matching the pattern shown in the official example (`'mic check'`). Exact byte limit unverified — keep the id short (e.g. base62, ~8-12 chars) to stay safely under any reasonable limit; do not block P0 on discovering the exact byte cap.
